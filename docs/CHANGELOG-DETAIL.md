## 0.6.8 (2026-09-20) — bugfix

### 修复
- **键盘 ↓ 越过可视区即「不跟随 / 跳回顶端 / 丢高亮」（此现象第 5 次才找到真因；0.6.4~0.6.7 连续四次都没修对）**：
  - **真因（事件层，第一次真正暴露）**：0.6.0 为「视图滚动时列表贴字段」在 `document` 上注册了
    **capture 捕获**的 scroll 监听 `repositionSuggest → showSuggest()`。scroll 事件虽不冒泡，
    但捕获阶段仍从 document 一路走向目标——于是**下拉自身的滚动**（`scrollActiveIntoView()`
    改 `suggestEl.scrollTop` 后，浏览器异步派发、目标是 suggestEl 本身的 scroll）也被捕获，
    随即调用 `showSuggest()` → `rebuildSuggestOpts()`：候选**整表重建**、`suggestActive=-1`、
    `setKbdNav(false)`，新内容把 `scrollTop` 钳回 0。用户可见的正是「走到可视区最后一条再按 ↓，
    不跟随、跳回顶端、无高亮，再按一次才高亮第一条」。重建出的选项是**全新节点**，
    指针下方的新节点会再触发 `mouseenter`（此时 kbdNav 已被重建复位 → 守卫失效），
    这就是 0.6.7 修了 kbdNav 仍残留「与我鼠标有点关系」的原因。
  - **修复**：`repositionSuggest` 识别事件来源——来自下拉自身（`e.target === suggestEl`）的
    scroll 一律忽略（它自己滚动不会改变它与定位上下文 `.tag-field` 的相对位置，本就无需重贴）；
    祖先容器滚动仍照常重定位。
  - **为何连续四次假绿灯**：jsdom 里 `scrollTop` 赋值**不会派发 scroll 事件**，
    这个事件路径在 0.6.4~0.6.7 四轮测试里**从未执行过**——测试与实现共享了
    「滚动不会有事件」这一共同盲区。
  - 本次用**真实无头 Chromium（playwright）**做了三方验证：
    （a）修复前可完整复现现场（事件序列：↓ → scrollTop=32 → scroll → 重建 → scrollTop=0、高亮 -1）；
    （b）还原旧实现 → 新回归用例失败于恰好的第 11 次 ↓（第一次触发滚动处）；恢复 → 通过；
    （c）修复后 40 项候选逐行跟随、高亮连续推进、↑ 回顶 scrollTop 归零。
  - 新增回归用例 ×1（jsdom 显式派发 scroll 模拟真实浏览器）+ 真实浏览器用例 ×1；
    全套 133/133 绿。顺手修复 ui-browser.test.ts 的 vite 入口解析（vite 8 起不导出 `vite/bin/vite.js`）。

### 测试增量
- `tests/ui-smoke.test.ts`：「0.6.8：下拉自身的 scroll 事件不得触发候选列表重建」——
  每次 ↓ 后显式派发 `Event("scroll")`（目标 = suggestEl，capture 监听在捕获阶段照样触发），
  断言 40 项全程高亮连续推进、scrollTop 逐行跟随、到底 clamp 不循环。
- `tests/ui-browser.test.ts`：「真实浏览器 0.6.8」——零注入，滚动即真实异步 scroll 事件，
  ↓ 打到底再 ↑ 回到顶，全程高亮不断、scrollTop 归零。

## 0.6.7 (2026-09-20) — bugfix

### 修复
- **键盘导航"失高亮 / 滚动条突然回顶"（此问题第 3 次修订，0.6.6 的修法本身是错的）**：
  用户实测：按 ↓ 走到可视区最后一条再按一次 → **失高亮**、滚动条只下移一点点；再按一次 →
  滚动条**回到最上面**、第一条露出来但仍无高亮；再按一次才高亮第一条。
  并明确反馈"**和我鼠标有点关系**，鼠标放在下拉表上面顺序就会乱一点"。
  - **真因**：0.6.6 用「500ms 时间窗」去挡鼠标的被动 `mouseenter`，而**时间窗会过期**。
    只要按键间隔超过 500ms（思考、找键位、慢慢按），保护就失效，`mouseenter` 又能抢走高亮。
    所以现象**取决于指针是否停在列表上、以及按键有多慢**——正是用户说的"和鼠标有关系"。
  - **修正**：把「键盘导航」从**时间窗**改成**显式粘性模式**（`kbdNav` 布尔量）：
    处于该模式时 `mouseenter` **一律不接管**，**只有真实的 `mousemove` 才退出该模式**。
    与按键快慢彻底无关。
  - **"滚动条回顶"是失高亮的连锁反应**，不是独立的滚动 bug：高亮被鼠标改到靠前的项后，
    下一次 ↓ 使 `itemTop < scrollTop` 成立，`scrollActiveIntoView()` 便按规则把滚动条上移。
    修好事件层后该现象自然消失。

- **`kbdNav` 与 CSS 类 `.kbd-nav` 双份状态易漂移**：新增唯一入口 `setKbdNav(on)`，
  同时改布尔量与类名。历史上出现过"只加类、没置位"的不一致（表现为 hover 被压制但高亮仍被抢），
  现在**禁止任何地方直接 `classList.add/remove("kbd-nav")`**。

### 关于本次排查（教训升级）
- **教训：不要用"计时器"去表达一个"模式"。** 0.6.6 的 500ms 免疫窗在快速按键下能通过测试，
  却挡不住慢速按键——**它把一个语义状态（我在用键盘）误建模成了一个瞬态事件（刚按过键）**。
  凡是"用户当前处于某种操作方式"的判定，都应当是显式状态，而不是"距上次操作 N 毫秒内"。
- **教训：用户说"和某样东西有关系"时，那就是最高价值线索**，说明现象依赖于某个被我忽略的变量。
  本轮的"和鼠标有点关系"直接指向了"判据随时间/指针位置变化"这个根因。
- **测试**：0.6.6 的用例用 4ms 间隔按键，**永远测不到计时器过期**（测试比 bug 跑得快）。
  现改为 **560ms 慢速按键**（大于旧的 500ms 窗口），旧实现必然失败、新实现必然通过——
  已双向验证：还原计时器守卫 → 用例失败（`1 !== 0`，正是"失高亮"）；恢复 → 通过。
  另验证了「真实 mousemove 必须能退出键盘模式」这条反向断言（禁用后用例失败）。

## 0.6.6 (2026-09-20) — bugfix

### 修复
- **键盘导航时高亮"闪没"并跳行（0.6.5 修错了方向，本版找到真因）**：
  用户实测"高亮 → 按下 → **没有高亮** → 按下 → 跳过没高亮的那条，直接到下一条"。
  真因**不在滚动算法，也不在行高**，而在 **`onmouseenter` 抢走了键盘高亮**：
  列表滚动时，**新的一行会滑到静止的鼠标指针下面**，浏览器随即对该行触发 `mouseenter`；
  而旧实现里 `mouseenter` **无条件**接管高亮，于是把用户刚按 ↓ 选中的那项 `.active` 抹掉
  （表现为"突然没有高亮"），下一次 ↓ 又从鼠标所在行往下走一格 → 看起来就"跳过了一条"。
  滚动条提前停住也是同一原因：高亮被鼠标反复改写，`scrollTop` 跟着回退。
  - 修正：**键盘导航后的 500ms 内忽略 `mouseenter`**；只有用户**真的移动鼠标**（`mousemove`）
    才立即清除该时间窗、恢复鼠标接管
  - 关键认知：`kbd-nav` 类**只管 CSS**（压掉 `:hover` 样式），对 JS 里那句
    `suggestActive = …` 毫无约束——这正是"加了 kbd-nav 仍然出问题"的原因

- **"遮蔽一半记录"（下拉上下边缘被切掉半行）**：
  真因是**行高被写死 32px，而 CSS 里的实际行高不是 32px**。
  `.opt` 的高度由 `font-size(12.5px) × line-height + padding(7px×2)` 自然撑开，
  实际落在 **26~33px** 之间浮动；于是 `maxRows × 32 + 2` 并不是**真实行高**的整数倍
  （实测：`maxHeight=322px` + 真实行高 29px → 320px = **11.03 行**），
  列表上下必然切进一行里。修正两层：
  1. **CSS 显式固定行高**：`.opt { height:32px; line-height:18px; box-sizing:border-box }`
     （内容区 18px = 行高 18px，恰好容纳，不裁字）
  2. **JS 按实测行高计算**（`measureRowH()`，取相邻项 `offsetTop` 差值），
     不再信任常量——这样即使将来 CSS 被改，也不会再次切半行

- **键盘导航时高度可能沿用旧值导致滚动提前停住**：抽出 `placeSuggest()`（只定位/定高、不碰内容），
  导航路径每次重新套用几何。旧版只写 `display="block"`，若上次是在可用空间更小时算的高度，
  `scrollTop` 上限就偏小 → "还没到最后一条，滚动条就停住不动了"

- **候选项抢焦点**：给 `.opt` 加 `tabindex="-1"`，并让 `.tag-field-box` 的点击处理器
  **排除建议列表内部**（`suggestEl.contains(e.target)`），避免点选项时焦点被夺走、`blur` 顺手收起列表

### 关于本次排查（记录以免重蹈）
- **教训一（修错方向的代价）**：0.6.4、0.6.5 连续两版都在"滚动算法/行高对齐"上找原因，
  方向都不对——真因是**事件层**（`mouseenter`）而非计算层。若一开始就按用户给的
  "同一可视范围内还会**失去高亮**"这一线索去查，本可一步到位。
  **下次遇到"视觉跳变 + 状态消失"同时出现，优先怀疑有事件在改写状态。**
- **教训二（假绿灯）**：0.6.5 的行高用例**自己注入了 `offsetHeight = 32`**，
  于是在"真实行高不是 32"这件事上**完全测不到**——它验证的是实现自己的假设。
  本版新用例改为注入**非 32 的真实行高（29px）**，并在把常量改回 32 时**确认失败**（已双向验证）。
- **教训三**：`kbd-nav` 这种"只改样式"的手段**不能替代状态层的守卫**，别再指望加个 class 就安全。
- 三个新用例均**已双向验证**（临时还原错误实现 → 用例失败 → 恢复 → 通过）：
  ① 伪 `mouseenter` 不得冲掉键盘高亮（含"真移动鼠标仍能接管"的反向断言）；
  ② 可视高度必须是**实测行高**的整数倍；③ 选中候选项后焦点仍留在输入框。

## 0.6.5 (2026-09-19) — bugfix

### 修复
- **下拉列表滚动"跳到上一条的下一条"（0.6.4 没修对，本版找到真因）**：
  用户实测"移到可视范围最后一条再往下，焦点马上又回到上面一条记录的下一条"。
  真因**不在滚动算法**，而在**列表高度不是整行数**：
  `max-height` 被夹到 320px，而 `.tag-suggest` 有 `border:1px`，border-box 下
  `clientHeight = 320 - 2 = 318px`，行高约 32px → **一屏 9.94 行**。于是滚到第 10 项时
  `scrollTop` 变成 2 / 34 / 66 …（**不是行高的整数倍**），顶部永远被切掉 2px，
  视觉上就像"列表没动、焦点跳回了上一条的下一条"。
  现两层修正：
  1. **列表高度取整行数**：按可用空间算出"最多几整行"（3~10 行），高度 = 行数×行高 + 边框，
     不再被 320 硬夹（如 10 行 = 322px，clientHeight 正好 320px = 整 10 行）
  2. **滚动按整行对齐**：每次滚动量都是行高的整数倍——高亮在下方时让它成为"最后一整行"，
     在上方时让它成为"第一整行"，顶部不再露半行

### 关于本次排查（记录以免重蹈）
- 0.6.4 的滚动实现（`scrollIntoView` → 自己改 `scrollTop`）方向是对的，但**没改掉高度非整行**这个前提，
  所以现象依旧
- **测试教训**：0.6.4 新增的滚动用例对**新旧两种算法都通过**——因为它只验"高亮是否完整可见"，
  而 318px 下按旧算法算出的可见性判定恰好也成立（差 2px）。真正锁住本 bug 的是
  新增的"**clientHeight 必须是行高整数倍**"断言：把高度改回 320 硬夹时该用例会失败，
  改回整行高度则通过（已双向验证）
- 另注：jsdom 下 `scrollIntoView` 是 `undefined`，旧代码用 `?.` 可选调用 → **在测试里从未真正执行**，
  是假绿灯；现测试改为注入行高 / `clientHeight` 来驱动滚动算法本身

### 测试
- 改写滚动用例为"整行对齐 + 高度整行"双重断言（含 ↓ 到底、↑ 回顶全程高亮完整可见），
  并双向验证该用例能捕获"高度被夹成非整行"的回归（当前 **129 例全绿**）

## 0.6.3 (2026-09-19) — feature

### 新增：标签区重构为 token field（标签与输入框合为一体）
用户反馈的"退格删标签看不见、像盲删"与"删除顺序随机"其实**同源**：标签（chips 区）和输入框是
上下两块、物理分离，退格是在下面的框里操作上面的东西，**没有光标指向被删对象**，只能靠额外的红色提示兜。
现按主流 tag input（Gmail / Twitter / Linear 同款）重构：

- **标签与输入框在同一个带边框的容器内**：光标紧贴最后一个 token，所见即所删，
  退格删标签就是"删光标前的东西"，与文本编辑一致，不再隔空操作
- **保留两段式保护且真正可见**：输入框为空时第一次退格 → 最后一个标签变红（**就在光标旁边，看得见**）；
  再按一次才删除；继续输入或新增标签自动取消。长按退格不会成串清空
- **点 `×` 直接删除**（精确操作走这条），删中间任意一个都不会误伤其它
- 点容器空白处焦点自动回到输入框；标签较多时框内自动换行并可滚动
- 建议列表改为对齐这个新容器，仍紧贴下沿展开（滚动/缩放时跟随）

### 变更：标签显示顺序 = 添加顺序
- **编辑界面按标签的添加顺序显示**（不再按拼音重排），"你怎么加的、就怎么显示"；
  退格删除的对象是**视觉上最后一个**，删的与看到的永远是同一个（此前的"随机感"源于
  显示按拼音重排、而删除按 Set 插入顺序取末尾，两者无关）
- **保存时按拼音排序落库**：跨收藏统一，同一批标签在各条记录、以及主面板搜索结果里顺序一致，
  看标签更整齐；**编辑已有收藏时按其存储顺序显示、不再重排**
- 判脏仍按标签**集合**比较，顺序变化不触发"未保存的修改"

### 测试
- 新增/改写 6 例：标签按添加顺序显示（刻意选拼音序不同的样本）、退格删的是视觉最后一个、
  长按退格不成串清空、输入框有内容时退格只删字、继续输入取消待删标记、
  保存按拼音落库且编辑时按存储顺序显示（当前 **126 例全绿**）

## 0.6.2 (2026-09-19) — bugfix

### 修复
- **退格键会成串清空已选标签（误操作）**：标签输入框为空时，此前每按一次退格就删除最后一个标签，
  用户一直按着（或连点）退格会把前面选定的标签**全部删掉**，很容易误操作。
  现改为**两段式删除**：
  1. 第一次退格**只把最后一个标签标记为「待删除」**（红色高亮 + 提示），不真删；
  2. **松手后再按一次**退格才真正删除；
  3. 期间继续输入内容、或新增标签，待删标记自动取消。
  另外加了**长按闩锁**：系统因按住不放而连续派发的 keydown（`e.repeat`）一律只做标记、
  不作确认，直到用户松手（keyup）才重新允许删除——因此**无论按住退格多久，最多只删掉一个标签**。
  输入框里有文字时退格照常只删文字，不受影响。
